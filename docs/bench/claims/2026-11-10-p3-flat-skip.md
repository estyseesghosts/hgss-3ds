## Dependency list (every input the flat picture depends on)

Covered by `EngineSmallSignature(e, snapshot, mask, 0, 0)` with `mask` =
committed text BGs (exactly as the non-flat reuse branch): display registers
(0x70, minus the 3D ack bits that flap every frame and MASTER_BRIGHT, which
the compositor applies on GPU), VRAM bank control (VRAMCNT), POWCNT swap bit,
BG palettes, OAM (incl. affine-vs-hidden semantics, which live here, not in
the VRAM range), per-line registers when active. Covered by
`SplitLayoutSignature`: canvas width/origin/clip, anchorWindows,
windowsToEdge, snapshot/height/top/stretch/gpuBgs, smooth-OBJ flag,
wide-windows serial, wide-art serial, window circles. Covered by the
referenced-range VRAM signature (`EngineReferencedOnly`, the referenced range
only, when modelled): map bytes, tile bytes and palettes the frame's layers
can actually read. Covered by the scroll check: committed-BG HOFS/VOFS
(scroll-only frames re-render). Covered by `RememberSplit` extension:
small+vram+scroll stored only when a flat render completes; the retained
quads/slots the caller keeps.

Not covered (take today's Render path): frames the referenced-range
signature does not model (`modelled == 0` — no fallback to the full 864 KB
hash here); non-flat pictures; engine B paths (untouched); any case the
diagnostic disagrees on (stop, do not ship with forced redraws).

## Implementation (what the code does)

`3ds_port/nitro/src/port_render2d.c`:

- `EngineReferencedOnly()`: the referenced-range signature **only**. Unlike
  `EngineVramSignature()` it never falls back to the full-VRAM hash: a frame
  the referenced set cannot model is reported "not modelled" and the caller
  keeps today's path (the plan's rule 2).
- `FlatStore()` (called from `RememberSplit()` when the render was flat):
  keeps `EngineSmallSignature(e, snapshot, mask, 0, 0) * 31 ^ layout`, the
  referenced-range VRAM signature and the committed BGs' scroll. The VRAM
  signature is only kept when `refHashA` is on: the skip rides that switch,
  and without it there is no signature that could stand in for the full hash
  (which must not be paid here). The retained VRAM signature is the one
  taken **before** the draw — see "The live-VRAM race" below.
- `FlatUnchanged()`: recomputes the same pair and compares, then checks the
  committed BGs' scroll. Returns 0 (today's path) if the frame is not
  modelled, if either signature differs, or if a committed BG scrolled.
- The flat branch of `NitroPort_Render2DSplitIfChanged()` skips the pass only
  when the picture is the same **and** the under/over/overAlpha buffers are
  the ones the picture was drawn into (the same condition the existing reuse
  branch uses).
- The diagnostic (`refHashDiag`): the pass always runs, and what it published
  (quad count, quad contents, slot keys, backdrop, has3d, scroll3d, tint3d,
  eva/evb/evy, flat flag) is compared with what the last flat pass published.
  A difference is counted and logged; the pass is redrawn either way.
- Counters: `NitroPort_Render2DFlatStats()` -> the shell's `[perf] flatskip:`
  line (skipped / redrawn / not-modelled / disagreements, and which input
  differed when a pass did not skip: small / vram / scroll / buffers). The
  "why" fields are what make a zero-skip result explainable instead of a
  mystery.

Both builds skip (it is a behaviour change, not instrumentation); the OFF
build is the timing build.

### Two places the plan's wording is not what the code does

1. The plan says "the caller already republishes the retained layers". It
   does not publish a new layer *set*: `RenderScreen()` returns false, so no
   `NitroPort_ComposePublish()` happens; the drawer marks the retained set
   current (`NitroPort_Compose2DCurrent()`) and the compositor keeps using
   the previous publication. The effect is the one the plan wants (the
   picture on screen stays, the 3D keeps composing), and it is the same path
   the existing reuse branch takes.
2. The plan's dependency list says the referenced-range signature is computed
   "only if" it models the frame. Modelling is only known after the
   computation, so the cost of the first, unmodelled attempt is paid. It
   bails at the first unmodelled BG, so it is bounded by one BG's map.

### Two more, found while measuring

3. **DISPSTAT and VCOUNT are left out of the change-detection hash.** The
   plan's step 1 hashes the whole 0x70-byte register block. With that, the
   skip never fired: the V-count in the snapshot moves with how much the
   game did since the V-blank, so every pass looked changed. Leaving those
   four bytes out is not "masking a register to increase hits" (the wiki's
   case study of this port warns against that): they draw nothing, the
   renderer never reads them, and the port's per-line registers already
   leave them out for exactly that reason. Everything else in the block
   (DISPCNT, the BG control and scroll registers, MOSAIC, the blend
   registers, the windows, DISP3DCNT's unmasked bits) is still hashed.
4. **The retained VRAM signature is taken before the draw, not after.**
   `NitroPort_Render2DTakeState` snapshots the registers, the palettes and
   the OAM, but the drawer reads the *tiles* live while the game's thread
   keeps writing them. A signature taken after the draw can describe tiles
   the picture on screen does not contain: the next pass's fresh signature
   then equals it, the skip fires, and the stale picture stays up until the
   game's next write. The legacy path avoids this by keeping the hash it
   took before its draw; the flat path now does the same. The plan's P4
   asks whether the skip can observe a torn state — it could, and this is
   the fix.

## The live-VRAM race

`NitroPort_Render2DTakeState` takes the engine's registers, palettes and OAM
at the handover ("what the game changes while it's being drawn doesn't get
mixed in"), but not the tiles: `SetUpEngine` reads VRAM live, and the game's
thread writes it. So every hash-based skip can race a game write.

The order of the two hashes is what decides whether the race can leave a
stale picture on the screen:

| retained signature | what it describes | the skip's verdict |
|---|---|---|
| taken **after** the draw | possibly tiles newer than the picture | the next pass's fresh hash equals it → skip → **the stale picture stays up** |
| taken **before** the draw | tiles at or older than the picture | the next pass's fresh hash differs if anything was written → redraw |

The flat path keeps the pre-draw one. A draw that captured none (the legacy
path's draws, which can also produce a flat picture) keeps **no** signature:
the next pass redraws once and captures its own.

The measurement the plan's P4 asks for is in the A0 diagnostic build: the
referenced range is hashed before and after every flat draw, and the passes
where the two differ are counted (`[a0] flat vram race: N draws hashed
before and after, M saw the game write VRAM during the draw`).

**Measured: M = 0, in both scripts** (Azahar, A0 build `9759707`):

```
[14400] [perf] flatskip: 600 skipped, 0 redrawn, 0 not-modelled, 0 disagreements, why small 0 vram 0 scroll 0 buffers 0
[14400] [a0] flat vram race: 3 draws hashed before and after, 0 saw the game write VRAM during the draw
```

P4's "stop and ask if the count is non-zero at rest" therefore does not
trigger. The caveat is the sample size: only 3 draws happen in a 600-tick
window (the picture is established and then never changes), so this shows
"the game wrote no tiles during those 3 draws", not "the game never writes
tiles while a draw is in flight".

**Still open (pre-existing, not introduced here):** the legacy reuse record
(`sSplitReuse[].vram`, kept by `RememberSplit()` after the draw) has the
same shape and is compared against a fresh pre-draw hash. A game write that
lands during a legacy draw can make the stored hash match the next fresh
one, and the reuse branch then keeps a stale picture. Fixing it means
taking the full VRAM hash before the draw (the legacy path's hash is the
whole 864 KB, not the referenced range), which is a cost decision of its
own — a separate claim sheet, not part of P3.

## Notes

- In split mode the software picture does not read the 3D image: a new 3D
  scene is not a reason to redo the flat picture.
- Never cache anything keyed on a pointer; never treat a scroll-only frame
  as unchanged (scroll check, not signatures).
- P4 (the VRAM-read race) is a separate packet in the plan; its question
  is answered here (the count is 0, and the retained signature is now the
  pre-draw one, which is what makes the count irrelevant).
- The frozen walk script's legs are 6-frame taps, so that A/B is a second
  rest measurement; `hg-field-walk2.txt` is the walking case.
