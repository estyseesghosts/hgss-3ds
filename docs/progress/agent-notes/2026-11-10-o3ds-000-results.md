## P3: the drawer's flat-picture skip

**What was built** (`845cae5`, PROFILE `98452ff8…` / OFF `913df823…`, both
clean at `845cae5`, default flags):

- `EngineReferencedOnly()` — the referenced-range VRAM signature with **no**
  full-VRAM fallback (the plan's rule 2: a frame the referenced set cannot
  model keeps today's path).
- `FlatStore()` / `FlatUnchanged()` — the pair that says "the same flat
  picture" (`EngineSmallSignature(e, snapshot, mask, 0, 0) * 31 ^ layout`, the
  referenced-range VRAM signature) plus the committed BGs' scroll. The skip
  rides `refHashA`; with it off there is no signature that could stand in
  for the full hash.
- The flat branch of `NitroPort_Render2DSplitIfChanged()` skips the pass only
  when the picture is the same **and** the under/over/overAlpha buffers are
  the ones the picture was drawn into.
- The `refHashDiag` diagnostic: the pass always runs, and what it published
  (quad count, quad contents, slot keys, backdrop, has3d, scroll3d, tint3d,
  eva/evb/evy, flat flag) is compared with what the last flat pass published.
- Counters: skipped / redrawn / not-modelled / disagreements, plus **which
  input differed** when a pass did not skip (small / vram / scroll / buffers),
  as `[perf] flatskip:`; `tools/bench_report.py` parses them.

**The premise holds.** In the field at rest the top pass really is flat: the
2D line reads `0 lines, 0 empty, 0 blend, rows 0/0`, `take 707 ms`,
`flatfill 122 ms`, `gpubg taken 1200, region 0/600` — the same picture,
re-validated every pass.

**The skip does not fire.** Azahar, `hg-continue-field.txt`, frames 9000+:

```
[16800] [perf] flatskip: 0 skipped, 600 redrawn, 0 not-modelled, 0 disagreements, why small 600 vram 0 scroll 0 buffers 0
```

Every pass differs in the *small* signature (the registers, palettes, OAM,
VRAM bank control and the layout). The A0 diagnostic splits it, and the
split is unambiguous — between two consecutive 600-tick samples:

```
[a0] redraw A: flat 9930 reuseHit 0 reuseScroll 0 forced 3 firstNote 0 layout 7 regs 12898 pal 501 oam 327 misc 13 vram 324 unchanged 259
```

`regs` grows by exactly 600 per window (one per pass); `layout`, `pal`,
`oam` and `misc` do not move at all. So the flat picture's registers change
on every single pass while its layout, palette, OAM and per-line registers
stay constant.

**The register is engine A's own.** Engine B, in the same run, takes the
legacy "unchanged" branch on every pass:

```
[a0] redraw B: flat 0 reuseHit 0 reuseScroll 0 forced 1 firstNote 0 layout 7 regs 530 pal 159 oam 138 misc 62 vram 131 unchanged 12723 mustDraw 1
```

`unchanged` grows by 600 per window while `regs` does not move at all. Both
engines hash the same shared registers (POWCNT1 at 0x304, VRAMCNT at 0x240)
and the same VCOUNT/DISPSTAT, so those cannot be the culprit — the word that
changes is in **engine A's own 0x70-byte block** (DISPCNT, the BG control
and scroll registers, MOSAIC, BLDCNT/BLDALPHA/BLDY, the windows, or
DISP3DCNT's unmasked bits). Engine A is the screen with the 3D.

**Which words** (a diagnostic build that compares the register block of this
pass with the one the last flat render used; the mask is the OR over every
pass, so it lists every word that ever differed):

```
[a0] flat regdiff: 15858 passes, word mask 0x01000083, bytes0-7 0x42, VRAMCNT 0, POWCNT1 0
```

| bit | word | offset | register | hashed? |
|---|---|---|---|---|
| 0 | 0 | 0x00 | DISPCNT | yes |
| 1 | 1 | 0x04 | DISPSTAT + VCOUNT | yes (the H-blank bit and the V-count) |
| 7 | 7 | 0x1C | BG3 HOFS/VOFS | no — masked out for a committed BG |
| 24 | 24 | 0x60 | DISP3DCNT | only its unmasked bits (12-13 are the ack bits) |

and the first eight bytes differ in bytes 0x01 and 0x06 — DISPCNT's second
byte and VCOUNT's low byte. VRAMCNT and POWCNT1 never differ.

**Which word differs on *every* pass: VCOUNT.** The diagnostic's second part
is the AND over the per-pass masks (the words that differ every time):

```
[a0] flat regdiff: 15858 passes, word mask 0x01000083, bytes0-7 0x42, VRAMCNT 0, POWCNT1 0, every 0x00000002, dispcnt1 0x07 (was 0x07)
```

`every 0x00000002` is word 1 alone — the 0x04-0x07 block, DISPSTAT and
VCOUNT. The byte mask says which of the four: `dispcnt1 0x07 (was 0x07)`,
so the high byte of DISPSTAT never changes and the difference is VCOUNT's low
byte (0x06). VCOUNT is the beam counter: its value in the snapshot depends
on how much the game did since the V-blank, so it moves every pass.

**Why leaving it out is safe (and not "masking a register to increase
hits").** The wiki's case study of this port
(`coffeepot/ctr/engineering/case-studies/case-study-hgss-port.md`) warns:
*"Do not mask a changing register merely to increase hits: first prove which
pixels, metadata and future states depend on it."* The proof, for
DISPSTAT/VCOUNT:

- **They draw nothing.** They are the H-blank flag, the V-blank flag, two
  interrupt flags and the beam counter. The port's own per-line registers
  already leave them out for exactly this reason (`KeepLine`: "not DISPSTAT
  and VCOUNT (0x04-0x07: they draw nothing, and the V-count is each line's
  own)").
- **The renderer never reads them.** `grep` over `port_render2d.c` for a read
  of 0x04-0x07 finds only the masking lines themselves (the old per-line
  path's `KeepLine` and the new one).
- **No future state depends on them.** They are not in the layout signature,
  not in the referenced-range VRAM set, not in the take's inputs, and not in
  the compositor's published state.

They are therefore left out of the change-detection hash in the same place
MASTER_BRIGHT and the 3D ack bits already are (`fc2a19b`).

### The live-VRAM race (P4's question, answered early)

The plan's P4 asks whether P3's skip can observe a torn state. It can — and
the first implementation had it.

`NitroPort_Render2DTakeState` snapshots the registers, the palettes and the
OAM, but **not** the tiles: the drawer reads VRAM live while the game's
thread keeps writing it. The first implementation stored the referenced-range
VRAM signature **after** the draw (`FlatStore`, called from `RememberSplit`
at the end of the draw). A signature taken after the draw can describe tiles
the picture on screen does not contain; the next pass's fresh signature then
equals it, the skip fires, and the stale picture stays up until the game's
next write. The legacy path does not have this: it stores its hash taken
*before* the draw (`last[e].vram = vram;` then `Render(...)`).

The fix (`fc2a19b`'s successor): the referenced-range signature is taken
**before** the draw, in the flat branch, and that one value is both what the
skip compares and what the draw retains. A draw that captured none (the
legacy path's) keeps no signature: the next pass redraws once and captures
its own. The order is then always conservative — the retained signature is
never newer than the picture.

The measurement P4 asks for is now in the A0 diagnostic build: the
referenced range is hashed before and after each flat draw, and the passes
where the two differ are counted (`[a0] flat vram race:`).
